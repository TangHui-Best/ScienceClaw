# RPA DOM 上下文工程评估原则

## 背景

在自然语言驱动浏览器操作的 RPA 场景中，LLM 的输入上下文不能简单等同于原始 DOM。原始 DOM 通常包含大量导航、布局、隐藏节点、重复组件和非任务相关文本；如果直接进入模型上下文，会稀释关键元素，降低意图识别与动作生成质量。

DOM 压缩过滤的核心目标不是“尽可能短”，而是在有限上下文中保留足够完成当前用户指令的可操作事实。

## 三项原则

### 1. 召回不能漏

用户指令相关的元素和邻近证据必须进入上下文。目标元素一旦被压缩阶段过滤掉，后续 planner 再强也只能基于缺失事实做猜测。

需要优先保留：

- 用户指令显式提到的文本、字段、按钮、链接、表格、列表、卡片、区域标题。
- 与目标元素相邻的 label、heading、placeholder、aria name、列名、行文本、分组标题。
- 可执行定位证据，例如 locator、role、frame path、row/column 相对关系、区域 scope。
- 对当前动作有约束作用的状态，例如 disabled、hidden、selected、checked、required、current URL/title。

评估问题：

- 如果用户说“点击第一行详情”，第一行、详情按钮、表头和所在表格是否都进入上下文？
- 如果用户说“填写审批人”，字段 label、输入控件、候选 autocomplete 行是否都能被看到？
- 如果目标在 iframe、弹窗、选区或滚动容器中，scope 信息是否保留下来？

### 2. 噪声要压低

上下文不是越全越好。无关节点过多会让 LLM 误判区域、选择错误元素，或生成过宽、过脆弱的定位策略。

应尽量压低：

- 全站导航、页脚、装饰按钮、隐藏模板、重复菜单、广告、埋点节点。
- 与当前指令无关的大段文本、无关表格、无关列表、历史区域。
- 仅有布局意义、缺少业务语义或操作价值的容器节点。
- 大量同质候选中没有排序、分组、摘要或采样策略的原始平铺数据。

评估问题：

- 上下文里与用户指令无关的交互元素是否明显多于相关元素？
- 重复组件是否被折叠成结构摘要，而不是逐个完整展开？
- 模型是否容易被导航栏、侧边栏或页面底部按钮干扰？

### 3. 结构要保真

高质量 DOM 压缩不是文本摘要，而是保留任务相关元素之间的关系。很多 RPA 错误不是因为模型没看到元素，而是看到元素后不知道它属于哪个表格、哪一行、哪个字段、哪个区域。

需要保真的结构关系包括：

- label 与 input/control 的绑定关系。
- table header 与 row/cell/action 的关系。
- card/list item 与其内部按钮、链接、状态文本的关系。
- detail section 与字段 label/value 的关系。
- iframe、弹窗、选区、滚动容器、tab 的上下文边界。
- 当前元素与可回放 locator 或 action schema 的对应关系。

评估问题：

- 表格行内按钮是否保留了“属于哪一行”的关系？
- 字段值是否保留了“属于哪个 label/section”的关系？
- 选区模式下，模型是否能区分“整页事实”和“用户选中的局部事实”？

## 后续对比使用方式

分析 ScienceClaw 与 browser-use 的 DOM 压缩过滤算法时，应围绕这三项原则比较：

- 召回策略：如何从用户指令、页面结构和可交互元素中找出相关候选。
- 去噪策略：如何限制无关 DOM、重复节点和低价值元素进入上下文。
- 结构表达：如何把 DOM 转换成 LLM 可理解、执行器可落地的页面事实。
- 失败表现：当压缩错误发生时，是漏召回、噪声干扰，还是结构关系丢失。

结论应优先回答：哪套算法更能在当前 RPA 目标下稳定保留“完成用户指令所需的可操作事实”，而不是简单比较上下文长度或元素数量。
