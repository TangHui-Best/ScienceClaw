# RPA Harness 资产录制与审查最小流程

> 生命周期说明：本文是当前资产录制与人工审查流程。判断资产正确性或 promotion 前
> 必须先读本文，但它是 guide，不是官方 Harness Feature/Evidence。相关交付记录包括
> F010/F015/F021/F022/F023 及其 EV 文档。

## 目的

这份文档回答一个问题：使用 Full SOP 录制生成 Harness 资产后，人和后续 Agent 应该如何协作，才能让资产既保留真实录制事实，又表达正确的人工预期。

核心原则：

```text
recorded facts are evidence
reviewed expectations are acceptance criteria
promotion is a human governance act
```

录制资产不等于资产已经正确。录制阶段保存的是事实：页面、trace、runtime output、生成代码、区域上下文和页面变化。资产是否能成为回归基线，取决于后续人工是否确认了执行结果预期、Skill 泛化预期、expected signals 和 sensitivity。

## 整体流程一览

```text
Full SOP 录制
  -> 生成 captured/draft 资产
  -> 生成 Review Packet
  -> 人工审查每步执行结果预期
  -> 人工审查生成 Skill 的泛化预期
  -> 判断资产用途：诊断 / candidate-lite / candidate / rejected
  -> 运行 deterministic profile 或相关 runner
  -> 修 RPA core、compiler 或重新录制
  -> 用同一资产 rerun
  -> 人工确认 expected signals 和 sensitivity
  -> 通过 CLI promote
```

最重要的边界是：录制事实可以由系统自动生成；正确性判断必须由人工审查确认。Agent 可以协助解释、提取差异和写报告，但不能自动把资产升为 `candidate` 或 `golden`。

## 资产文件结构

一个 Full SOP Harness 资产通常长这样：

```text
<asset_root>/<asset_id>/
  scenario.json
  review.md                         # run_asset_review 生成的人类审查入口
  execution_review.md               # run_asset_execution_review 生成的执行链路审查入口
  steps/
    001/
      checkpoint.json                # 该步骤的页面前后状态、运行状态、trace 路径
      trace_events.json              # 该步骤实际录制出来的 accepted trace
      expected.json                  # 该步骤的机器可执行期望信号草稿/审查后信号
      before.html                    # 执行前页面证据
      after.html                     # 执行后页面证据，可能复用 before
      failure.json                   # 失败步骤才可能有
    002/
      ...
```

各文件职责如下：

| 文件 | 记录什么 | 谁写入 | 人工审查重点 |
| --- | --- | --- | --- |
| `scenario.json` | 资产级元数据、生命周期、promotion 状态、runner modes、sensitivity review 状态。 | 录制/治理 CLI | 资产是否还是 `captured`，是否允许进入 `candidate-lite` / `candidate`。 |
| `steps/<NNN>/checkpoint.json` | 单步意图、录制模式、before/after 页面、runtime status、trace 路径。 | 录制系统 | 该步页面变化是否符合人的 SOP 意图。 |
| `steps/<NNN>/trace_events.json` | 真实录制事实：动作、AI 代码、输出、区域上下文、output key。 | 录制系统 | 事实是否暴露了 runtime、planner、selector、extraction 或 dataflow 问题。 |
| `steps/<NNN>/expected.json` | 单步 runner 可读取的期望信号。 | 自动草稿，人工审查后才可信 | 是否表达正确业务预期，是否错误地接受空输出或硬编码现场值。 |
| `before.html` / `after.html` | 页面证据。 | 录制系统 | 页面中是否实际存在目标文本、列表、按钮或区域结构。 |
| `review.md` | 人类可读审查包：SOP、输出、自动检查、生命周期建议。 | `run_asset_review` | 是否需要补充人工结论、正确预期和 promotion 决策。 |
| `execution_review.md` | 人类可读执行审查包：汇总 stateful/skill/compiler/snapshot runner 结果。 | `run_asset_execution_review` | SOP→Skill 链路是否触发、失败归因是否清楚、是否存在模型配置注入边界差异。 |
| `docs/rpa/harness/reports/*.md` | 跨 Agent 的诊断/交接报告。 | Agent 或人工 | 记录为什么该资产用于诊断、修复、promotion 或 rejection。 |

`scenario.json` 和 `checkpoint.json` 会重复出现 URL、状态和路径信息，这是有意的索引冗余：

- `scenario.json` 管整个资产：它回答“这是什么资产、包含哪些步骤、当前治理状态是什么、能不能被 runner 选中”。
- `checkpoint.json` 管单个步骤：它回答“这一步的意图是什么、执行前后页面在哪里、trace 和 expected 文件在哪里、运行状态是什么”。
- `trace_events.json`、HTML 和 `expected.json` 才是具体证据和期望信号本体。

也就是说，runner 和 Agent 先读 `scenario.json` 判断资产级资格，再读每个 `checkpoint.json` 找到 step 级证据文件，最后才打开较大的 HTML、trace 和 expected 内容做具体分析。

不要把 `runtime_status=success` 等同于资产通过。它只说明运行时认为该步骤完成，不说明业务结果正确，也不说明生成 Skill 足够泛化。

## 该写到哪里

| 信息类型 | 首选记录位置 | 说明 |
| --- | --- | --- |
| 录制时实际输出 | `trace_events.json` | 不要为了让资产“看起来正确”篡改事实。 |
| 单步执行结果预期 | `steps/<NNN>/expected.json`，并在 `review.md` 或报告里解释 | `expected.json` 是 runner 入口；人工解释用于交接。 |
| 单步 Skill 泛化预期 | `steps/<NNN>/expected.json` 的 `compiler_signals`，并在 `review.md` 或报告里解释 | 例如不得硬编码现场值、必须保留 `output_key`。 |
| 人工发现的执行结果偏差 | `review.md` 或 `docs/rpa/harness/reports/<date>-<asset>-triage.md` | 说明 recorded output 与正确预期的差异。 |
| 人工发现的 Skill 泛化偏差 | `review.md` 或 triage report | 说明 generated Skill 为什么不满足 replay 预期。 |
| 资产能否升级 | `scenario.json` 的治理字段，由 promotion CLI 修改 | 不要手改 JSON 绕过确认。 |
| 修复任务和长期工程记忆 | 对应 Feature / Evidence / Backlog | 只有触发 RPA core 修复或长期交接时才需要。 |

如果当前工具自动生成的 `expected.json` 与人工判断冲突，以人工审查结论为准；但应通过后续工具或修复流程让 `expected.json` 也表达正确的机器可执行预期。

## 录制中发现执行结果不符合预期

如果录制时已经看到某一步结果不对，例如“提取列表”返回空数组，但页面上实际有列表数据，不要把资产丢掉，也不要把错误输出当作正确预期。

正确处理方式是把资产标记为诊断资产：

```text
asset_status: draft
promotion_status: captured
expected_signals_reviewed: false
sensitivity_reviewed: false
```

然后在 `review.md` 或 triage report 中写清楚人工验收标准：

```text
Step: <step_index>
Intent: <人的步骤意图>
Recorded output: <trace_events.json 中的实际输出>
Expected result:
- <正确输出应满足的结构、字段、数量或文本条件>
- <哪些情况下允许为空，哪些情况下不允许为空>
Observed evidence:
- <before/after HTML 或 trace 中证明页面事实存在的证据>
Likely owner:
- <RecordingRuntimeAgent / snapshot / extraction / expected signal drafting 等>
Promotion decision:
- 不允许升为 candidate/golden
- 可保持 captured，或人工确认后作为 candidate-lite 诊断观察
Verification after fix:
- <修复后需要 rerun 的命令或字段>
```

这里的关键是区分：

| 内容 | 含义 |
| --- | --- |
| `trace_events.json` 里的 output | 录制时实际发生的事实，哪怕是错的也要保留。 |
| `expected.json` 里的 reviewed signal | 人工确认后的机器可执行期望信号，不能盲信错误输出。 |
| `review.md` / triage report | 人和 Agent 的交接入口，说明事实和正确预期的差异。 |

如果自动生成的 `expected.json` 把错误输出写成 `allow_empty_output=true`，人工审查应明确覆盖这个判断：该字段只是自动草稿，不是已审查的正确预期。

## 录制结果正确但生成 Skill 不符合预期

另一类常见情况是：录制时结果正确，但生成的 Skill 脚本不够泛化，例如硬编码了现场项目名、现场 URL、现场文本、固定列表项或临时 selector。

这类资产仍然有价值，但它证明的是 compiler / generalization 问题，而不是业务步骤失败。

审查时应写清楚 Skill 泛化验收标准：

```text
Step: <step_index>
Intent: <人的步骤意图>
Recorded behavior: <录制时成功完成了什么>
Expected replay behavior:
- <未来 replay 应如何根据当前页面事实完成同一业务目标>
- <不得依赖哪些录制现场值、排序、URL、文本或 selector>
Compiler expectation:
- generated Skill 不应硬编码 <observed value>
- generated Skill 必须保留 <output_key / region context / dataflow reference>
Observed compiler problem:
- <compiler-hardcoded-observed-value / output_key lost / dataflow lost 等>
Likely owner:
- TraceSkillCompiler / trace dataflow / semantic action compilation
Promotion decision:
- 不允许作为 blocking candidate，除非该泛化问题被修复并 rerun 通过
Verification after fix:
- compiler regression 不再报告对应 failure category
- generated Skill 满足 replay 预期
```

判断标准：

| 正确事实 | 仍可能是失败 |
| --- | --- |
| 录制时点到了正确项目 | Skill 把这个项目名写死。 |
| 录制时提取到了详情文本 | Skill 直接写死详情文本，而不是从页面区域提取。 |
| 录制时拿到了列表结果 | Skill 只适配这一次 DOM 偶然路径，不能换页面数据 replay。 |

所以，执行结果验收标准和 Skill 泛化验收标准是两层不同的预期：

```text
execution acceptance: 当前步骤是否真的完成了业务目标
skill generalization acceptance: 编译后的 Skill 是否能泛化 replay 这个业务目标
```

## expected signals 与 sensitivity

`expected signals` 是期望信号，主要是单步级别的机器可执行验收信号，位于 `steps/<NNN>/expected.json`。

常见分组：

| 分组 | 含义 |
| --- | --- |
| `state_signals` | 输出字段、输出类型、是否允许为空、URL 是否应变化等。 |
| `compiler_signals` | 生成 Skill 必须保留或禁止的内容，例如 `output_key`、dataflow、不得硬编码现场值。 |
| `snapshot_signals` | raw / compact snapshot 应保留的页面文本、区域、候选结构。 |
| `action_signals` | 动作类型、目标元素、区域选择、目标上下文。 |

资产级别的覆盖范围和是否进入回归基线，不靠单个 `expected.json` 决定，而是由 `scenario.json` 的 governance 字段和 promotion 状态决定。

`sensitivity` 是资产敏感性分级，不是“自动保证没有敏感数据”。常见含义：

| 字段 | 含义 |
| --- | --- |
| `sensitivity: local-only` | 默认新资产只留本地，不应随意提交或外发。 |
| `sensitivity: sanitized` | 已做过脱敏处理，但仍需看具体边界。 |
| `sensitivity: repo-safe` | 人工确认可进入仓库。 |
| `sensitivity: sensitive` | 只能留在受保护位置。 |
| `sensitivity_reviewed: true` | 人已经确认当前敏感性分级和保存/分享方式可接受。 |

### 敏感扫描与脱敏 replay contract

`sensitivity_reviewed=true` 不是扫描动作本身。它只能表示人已经基于证据确认了敏感性分级和保存/分享方式。进入人工确认前，应先运行确定性扫描：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_sensitivity_scan --assets <asset_root> --asset-id <asset_id>
```

默认报告会写入：

```text
<asset_root>/<asset_id>/sensitivity_scan.json
```

`run_asset_review` 会把扫描结论写入 `review.md` 的 `Sensitivity Scan` 区块，包括风险等级、建议敏感级别、是否阻断 `repo-safe`、命中类别和脱敏 replay contract 状态。跨资产或 CI 需要汇总报告时，可以显式传 `--output <report_path>`；单资产审查报告应优先保留在资产目录内。

敏感网页常见有两类资产价值：

| 场景 | 不应保留 | 应保留 |
| --- | --- | --- |
| 登录页 | 真实账号、密码、cookie、session token。 | 输入字段角色、登录动作、运行时 secret 引用，例如 `LOGIN_USERNAME` / `LOGIN_PASSWORD`，或 controlled login fixture。 |
| 交易/账务页 | 真实金额、账号、卡号、个人信息。 | 字段语义，例如 `currency_amount`、`account_identifier`；数据形态，例如 `money`、`masked_account`；页面区域和提取行为。 |

脱敏后资产仍要能执行，不能只把敏感值删空。推荐在 `expected.json` 中保留 `state_signals.sanitization_contract`：

```json
{
  "state_signals": {
    "sanitization_contract": {
      "placeholders": [
        {
          "token": "<AMOUNT_1>",
          "semantic_type": "currency_amount",
          "shape": "money"
        }
      ],
      "runtime_secret_refs": ["LOGIN_USERNAME", "LOGIN_PASSWORD"],
      "controlled_fixtures": ["login-page"],
      "replay_assertions": [
        "amount field is present",
        "amount shape is money"
      ]
    }
  }
}
```

判断标准：

| 资产状态 | replay 要求 |
| --- | --- |
| raw sensitive asset | 可留本地诊断，但不应进入 `repo-safe`；若无 contract，不应升 blocking candidate。 |
| sanitized asset | 真实值替换为占位符，同时保留字段语义、形态和 replay assertion。 |
| login / password SOP | 凭证由运行时 secret 或 controlled fixture 注入，不写入资产。 |
| financial SOP | 验证字段角色、金额形态、区域定位和提取行为，不验证真实金额。 |

## 资产状态选择

| 状态 | 什么时候用 | 是否 blocking |
| --- | --- | --- |
| `draft/captured` | 新录制、未审查、发现结果错误、敏感性未确认。 | 否 |
| `candidate-lite` | 人工确认有诊断价值，但 expected/sensitivity 或泛化质量未达 blocking 标准。 | 否 |
| `candidate` | 人工确认执行结果预期、Skill 泛化预期、expected signals、sensitivity，适合作为回归基线。 | 是 |
| `golden` | 长期稳定、低维护、代表核心能力，并经人工批准。 | 是 |
| `rejected` | 资产事实无效、不可复现、敏感不可保留，或不再有诊断价值。 | 否 |

不要因为一次录制 `runtime_status=success` 就 promotion。`success` 只表示运行时认为步骤完成，不表示人类业务预期和 Skill 泛化预期都正确。

## Agent 交接最小信息

把资产交给另一个 Agent 时，至少提供：

```text
Asset:
<asset_root>/<asset_id>

Human SOP:
1. ...
2. ...

Review packet:
<asset_root>/<asset_id>/review.md

Known expectation gaps:
- Step N recorded output vs expected result
- Step M generated Skill vs expected replay behavior

Current lifecycle:
- asset_status=...
- promotion_status=...
- expected_signals_reviewed=true/false
- sensitivity_reviewed=true/false

Do not:
- 不要把 runtime_status=success 当成通过
- 不要手改 governance JSON 绕过 review
- 不要为了通过而加站点特定 Harness 规则
- 不要用 live URL 当正确性来源

Next action:
- 修 RPA core / 修 compiler / 重新录制 / 升 candidate-lite / 升 candidate

Verification after fix:
- 运行哪些 Harness 命令
- 哪些字段必须变化
```

如果这些信息缺失，后续 Agent 应先追问，不应猜测资产是否正确。

## 推荐命令顺序

新资产审查：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_review --assets <asset_root> --asset-id <asset_id>
```

资产校验：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_validation --assets <asset_root> --output tmp-harness-validation.json
```

敏感扫描：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_sensitivity_scan --assets <asset_root> --asset-id <asset_id>
```

该命令默认生成：

```text
<asset_root>/<asset_id>/sensitivity_scan.json
```

默认稳定 profile：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_harness_profile --assets <asset_root> --profile deterministic --output tmp-harness-profile-deterministic.json
```

执行审查报告：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_execution_review --assets <asset_root> --asset-id <asset_id>
```

该命令默认生成：

```text
<asset_root>/<asset_id>/execution_review.md
```

它读取同一资产目录下的 `stateful_sop_execution_report.json`、`skill_replay_execution_report.json`、`compiler_execution_report.json` 和 `snapshot_execution_report.json`。报告用于给人看，不替代底层 JSON；如果报告出现模型凭证缺失，应先区分“真实服务入口是否有凭证”和“Harness runner 是否注入了服务层解析后的 `model_config`”。

需要让 governed/profile runner 模拟真实服务的 runtime AI 凭证注入时，使用 Harness-only 模型配置文件：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_governed_regression --assets <asset_root> --model-config-file <local_model_config.json>
python -m backend.rpa.harness.run_harness_profile --assets <asset_root> --profile deterministic --model-config-file <local_model_config.json>
```

`local_model_config.json` 应使用运行时需要的字段名，例如 `model_name`、`base_url`、`api_key`、`provider`。不要把该文件提交到仓库，也不要写入资产目录。runner 报告只应记录 `runtime_ai_model_config_source`，不应记录真实密钥。

升级到 warning-only observation：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_promote --assets <asset_root> --asset-id <asset_id> --level candidate-lite
```

升级到 blocking candidate：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_promote --assets <asset_root> --asset-id <asset_id> --level candidate --confirm-expected --confirm-sensitivity
```

## 脱敏资产副本

如果敏感扫描发现 raw asset 只能保留在本地，但该资产仍有 SOP / Skill replay 价值，应优先生成派生脱敏副本，而不是原地改写 raw evidence。

推荐命令：

```powershell
$env:PYTHONPATH='RpaClaw'
python -m backend.rpa.harness.run_asset_sanitize --assets <asset_root> --asset-id <raw_asset_id> --target-asset-id <raw_asset_id>-sanitized --overwrite
python -m backend.rpa.harness.run_asset_sensitivity_scan --assets <asset_root> --asset-id <raw_asset_id>-sanitized
python -m backend.rpa.harness.run_asset_review --assets <asset_root> --asset-id <raw_asset_id>-sanitized
python -m backend.rpa.harness.run_asset_execution_review --assets <asset_root> --asset-id <raw_asset_id>-sanitized
```

脱敏副本应满足：

| 字段或文件 | 要求 |
| --- | --- |
| `scenario.json` | `asset_id` 改为派生 id，`sensitivity=sanitized`，`environment.sanitized_from_asset_id=<raw_asset_id>` |
| `sanitization_report.json` | 记录替换出的占位符、语义类型和 raw asset preserved 事实 |
| `steps/*/expected.json` | 写入 `state_signals.sanitization_contract`，保留 placeholders、runtime secret refs、controlled fixtures、replay assertions |
| `sensitivity_scan.json` | 不应有 repo-safe blocking finding；常见允许项是 `sanitized-placeholder` 与 `public-web-noise` |
| `review.md` | 必须展示 `Sensitivity Scan` 结论，并说明是否仍需人工 expected/sensitivity review |
| `execution_review.md` | 必须汇总 execution runner 的可读结论，并说明失败是资产/编译/回放/配置注入中的哪一类边界 |

脱敏不是删空敏感值。登录、交易、财务等页面应把真实值替换为语义占位符或 runtime secret reference，使后续脚本仍能验证字段角色、数据形态、页面区域和 SOP 行为。HTML 或 JSON 转义后的敏感值也要纳入扫描与脱敏，例如 `C:\\Users\\...`、`C:<span>\\</span>Users...` 这类网页渲染形态。
